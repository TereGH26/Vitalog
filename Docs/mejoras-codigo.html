Auditoría defensiva de VitaLog

Estado analizado: 23 de noviembre de 2026 · Frontend React, backend Spring Boot y persistencia MongoDB

Alcance. Análisis estático y pasivo del frontend React, servicios HTTP, autenticación y sesión, seguridad Spring, controladores y DTO de hábitos, persistencia, manejo de errores, pruebas recientes y cambios de interfaz observados. Se incluyeron también las credenciales locales y exclusiones de Git como factores operativos, sin revelar sus valores en este documento.

Resumen ejecutivo

El diseño actual protege correctamente los hábitos con una sesión autenticada: el correo se obtiene del principal y no se acepta como identificador elegido por el cliente. Las respuestas no incluyen el correo propietario. React usa renderizado escapado de texto y no se encontró almacenamiento de sesión en localStorage, sessionStorage ni secretos JWT en código fuente.

Las mejoras prioritarias son verificar los atributos reales de las cookies en ejecución, cubrir la autorización HTTP y CSRF con pruebas, limitar la duración máxima de hábitos y evitar que errores de base de datos revelen rutas y detalles operativos. No se encontraron evidencias suficientes para declarar una vulnerabilidad crítica o alta confirmada.

1. Vulnerabilidades y seguridad

MEDIA Atributos de sesión y cookies no verificables desde el código estático

Confianza
Alta en el mecanismo observado; media en el impacto concreto del despliegue.
Ubicación
SecurityConfiguration.java, authService.js, habitService.js, propiedades de aplicación.
Evidencia
Existe protección CSRF mediante csrf.spa(); el frontend obtiene XSRF-TOKEN y lo envía en X-XSRF-TOKEN. No se declaró explícitamente Secure, HttpOnly, SameSite, caducidad de sesión ni una sesión renovada después del login. No se inspeccionaron cabeceras reales.
Impacto
Un despliegue externo mal configurado podría ampliar la exposición de la sesión o cambiar el comportamiento CSRF. No se encontró una cookie insegura confirmada ni se ejecutó la aplicación.
Recomendación
Exigir HTTPS, verificar Set-Cookie en el entorno real y configurar la cookie de sesión como HttpOnly, Secure y con una política SameSite compatible. Mantener CSRF activo y revisar caducidad y renovación al autenticar.

MEDIA Falta de pruebas HTTP que demuestren autorización y aislamiento entre cuentas

Confianza
Alta en la ausencia de cobertura observada.
Ubicación
SecurityConfiguration.java, HabitController.java, App.test.js, pruebas JUnit.
Evidencia
/api/habits y /api/habits/** requieren autenticación. Las pruebas del servicio y React no ejercitan una solicitud HTTP anónima, una operación sin CSRF, ni dos usuarios consultando datos separados.
Impacto
Una revisión futura podría relajar reglas de acceso sin que las pruebas actuales lo detecten.
Recomendación
Añadir pruebas MockMvc para 401 sin sesión, POST sin CSRF, POST con CSRF, datos separados entre dos cuentas y rechazo de rutas no previstas.

MEDIA Credencial local existente fuera del control de código versionado

Confianza
Alta sobre su presencia local; media sobre exposición real.
Ubicación
Vitalog/.env, Vitalog/.gitignore.
Evidencia
Existe una URI MongoDB local con credenciales en .env. El archivo está excluido explícitamente por .gitignore; no se encontró la credencial real dentro de archivos Java o JavaScript versionados.
Impacto
Si el equipo comparte copias, imágenes o archivos sin excluirla, o expone el puerto, la credencial podría reutilizarse. Al ser localhost y estar excluida, no hay evidencia de un compromiso confirmado.
Recomendación
Rotar la credencial si fue compartida o comprometida, usar usuarios distintos por entorno y mantener secretos fuera de artefactos, logs y documentación.

BAJA Cifrado de contraseñas y normalización de correo confirmados

Confianza
Alta.
Ubicación
SecurityConfiguration.java, UserAccountService.java, RegisterRequest.java, UserAccountRepository.java.
Evidencia
Las contraseñas se cifran con BCryptPasswordEncoder(12). El correo se valida y normaliza a minúsculas. React aplica los cinco requisitos y backend vuelve a validar.
Impacto
Control positivo contra almacenamiento de texto plano y registros duplicados por mayúsculas. No sustituye limitación de intentos ni controles operativos.
Recomendación
Conservar estas reglas y considerar límite de intentos, auditoría de autenticaciones y bloqueo temporal si el entorno lo requiere.

BAJA Protección XSS directa no encontrada en el frontend revisado

Confianza
Alta.
Ubicación
HomePage.js, AuthPage.js, fuentes React.
Evidencia
Los datos se representan como expresiones React, por ejemplo {habit.name}. No se encontró dangerouslySetInnerHTML, propiedades CSS inyectadas ni HTML construido con datos del usuario.
Impacto
React escapa el contenido de texto, reduciendo el riesgo de ejecución de código desde nombres o mensajes. No se ha probado a nivel dinámico con caracteres maliciosos.
Recomendación
Mantener el renderizado seguro y añadir una prueba con texto que contenga HTML y caracteres especiales.

2. Seguridad y validación de hábitos

MEDIA Duración sin límite máximo ni alineación de rangos

Confianza
Alta.
Ubicación
CreateHabitRequest.java, HabitService.java, HomePage.js.
Evidencia
Backend exige @Min(1), pero no @Max. Frontend exige entero positivo y tampoco tiene máximo. Se usa 66 como valor predeterminado.
Impacto
Datos desproporcionados pueden afectar presentación, cálculos futuros o persistencia lógica. Es un riesgo de integridad y uso abusivo, no una inyección confirmada.
Recomendación
Acordar un máximo de producto y aplicarlo igual en backend y frontend. Añadir límites para nombres al máximo permitido y casos superiores e inferiores.
Ejemplo ilustrativo mínimo
@Min(value = 1)
@Max(value = 365, message = "La duración máxima es 365 días.")
Integer durationDays;

MEDIA Aislamiento positivo por cuenta para crear y listar hábitos

Confianza
Alta sobre el código.
Ubicación
HabitController.java, HabitService.java, HabitRepository.java, HabitResponse.java.
Evidencia
list y create reciben @AuthenticationPrincipal UserDetails. El servicio guarda y consulta por su nombre de usuario. El cliente no puede enviar accountEmail como entrada ni la respuesta lo devuelve.
Impacto
Reduce el riesgo de cruce de datos entre cuentas. Debe mantenerse cubierto por pruebas HTTP posteriores.
Recomendación
No permitir búsquedas por una cuenta suministrada por el cliente y conservar el principal autenticado como única fuente de propiedad.

BAJA Validación dual y normalización son positivas, con casos de Unicode pendientes

Confianza
Alta.
Ubicación
passwordValidation.js, AuthPage.js, CreateHabitRequest.java, HabitService.java, HabitServiceTests.java.
Evidencia
Correo, contraseña, nombre, duración, frecuencia y días tienen validación cliente/servidor o reglas de servicio. Las pruebas cubren duración, días semanales y requisitos de contraseña.
Impacto
No se encontró que el backend confíe en la UI. Faltan casos de Unicode, espacios, nombres al límite y entradas duplicadas o ambiguas.
Recomendación
Añadir pruebas equivalentes para ambos niveles y mantener mensajes consistentes. Eliminar alias ambiguos si el requisito no los necesita.

3. Persistencia y manejo de MongoDB

MEDIA Los errores de MongoDB revelan detalles operativos al cliente

Confianza
Alta sobre el código; impacto operativo condicionado.
Ubicación
ApiExceptionHandler.java, application-local.properties.
Evidencia
Ante DataAccessException, la respuesta menciona MONGODB_URI, una ruta relativa y el reinicio del servicio.
Impacto
Un usuario que observe el fallo recibe información útil para reconocimiento operativo. Los detalles técnicos deberían permanecer en logs protegidos.
Recomendación
Responder con un mensaje estable y genérico, registrar la causa y un identificador de correlación interno, y reservar instrucciones de configuración para operación.

MEDIA Falta un manejador explícito para excepciones generales no previstas

Confianza
Alta sobre la ausencia de una ruta general; impacto condicionado.
Ubicación
ApiExceptionHandler.java.
Evidencia
El manejador cubre validación, MongoDB y reglas específicas de hábitos y cuentas, pero no se encontró @ExceptionHandler(Exception.class) ni respuesta genérica 500.
Impacto
Errores inesperados podrían depender del contenedor o mostrar información distinta entre entornos.
Recomendación
Añadir respuesta 500 estable sin trazas ni detalles internos y mantener el registro técnico con trazabilidad.

OPORTUNIDAD Consulta por cuenta sin índice compuesto declarado

Confianza
Alta sobre la consulta; impacto real no medido.
Ubicación
Habit.java, HabitRepository.java.
Evidencia
findByAccountEmailOrderByStartDateDesc filtra por correo y ordena por fecha. No se encontró anotación o creación automática de índice.
Impacto
Con pocos datos no será relevante. Al crecer el volumen, MongoDB podría recorrer documentos y ordenar resultados.
Recomendación
Evaluar un índice compuesto { accountEmail: 1, startDate: -1 }, validar planes de ejecución con datos representativos y desplegarlo de forma controlada.

OPORTUNIDAD Listado completo sin paginación ni límite

Confianza
Alta sobre el comportamiento; impacto por volumen no medido.
Ubicación
HabitController.java, HabitService.java, HabitRepository.java, HomePage.js.
Evidencia
El servicio devuelve todas las coincidencias de una cuenta y React las conserva en una sola lista sin virtualización ni paginación.
Impacto
Puede crecer el tiempo de serialización, el tamaño de red y la memoria del navegador. No existe evidencia de volumen suficiente para llamarlo vulnerabilidad confirmada.
Recomendación
Introducir paginación o límite después de medir cargas representativas, manteniendo cuenta y orden descendente por fecha.

4. React, cambios recientes y arquitectura

MEDIA El cambio reciente abre/cierra el formulario, pero no ofrece cancelación ni gestión de foco

Confianza
Alta sobre el estado actual; media sobre el requisito de UX.
Ubicación
HomePage.js, App.test.js, App.css.
Evidencia
isHabitFormOpen comienza en falso, el botón abre el panel y el éxito lo cierra y restablece campos. Las pruebas cubren apertura, duración 66, diaria y cierre tras guardar. No hay botón Cancelar ni foco movido al abrir/cerrar.
Impacto
No se encontró pérdida de datos por React. El usuario puede quedar sin una salida explícita hasta guardar o salir de la pantalla, y el foco puede permanecer fuera del nuevo contenido.
Recomendación
Añadir Cancelar, mover el foco al campo principal al abrir y devolverlo al botón Crear al cerrar. Probar cancelación, éxito y fallo con roles accesibles.

BAJA Efectos React limpios, con responsabilidad concentrada en HomePage

Confianza
Alta.
Ubicación
App.js, HomePage.js, AuthPage.js.
Evidencia
Los efectos usan banderas active y limpieza al desmontar. El formulario y el listado están en estado local. HomePage combina presentación, validación, solicitudes y sesión visual.
Impacto
La página es funcional y evita una actualización obvia tras desmontar. La concentración de responsabilidades puede aumentar la deuda de mantenimiento.
Recomendación
Separar componentes de formulario/listado si crece la pantalla y centralizar validaciones o contratos HTTP. Mantener limpieza o adoptar cancelación de solicitudes.

OPORTUNIDAD Cobertura reciente amplia en UI, pero incompleta en errores y seguridad HTTP

Confianza
Alta.
Ubicación
App.test.js, HabitServiceTests.java, UserAccountServiceTests.java.
Evidencia
Las pruebas cubren formularios, contraseña, duración y hábito semanal. Faltan cancelación, errores de API, 401/403, CSRF, aislamiento, límites superiores y carga/paginación.
Impacto
Las pruebas existentes protegen cambios principales, pero no demostraciones de seguridad ni regresiones de acceso.
Recomendación
Ampliar React Testing Library y añadir pruebas de seguridad Spring. Mantener pruebas aisladas y sin modificar datos reales.

OPORTUNIDAD Lectura CSRF duplicada puede centralizarse

Confianza
Media.
Ubicación
authService.js, habitService.js.
Evidencia
Ambos módulos implementan por separado la lectura de XSRF-TOKEN y el refresco.
Impacto
Actualmente son coherentes. Una modificación futura podría actualizar sólo una ruta y romper el envío CSRF.
Recomendación
Centralizar cookie, refresco y cabecera CSRF en una utilidad HTTP compartida.

Controles positivos confirmados

  • Los endpoints de hábitos usan el principal autenticado; no hay un correo solicitado por el cliente para seleccionar la cuenta.
  • Las respuestas de hábito excluyen accountEmail.
  • El backend valida entradas con Bean Validation y el servicio vuelve a comprobar frecuencia y duración mínima.
  • No se encontró inyección de HTML, JWT expuesto ni tokens de sesión en almacenamiento web.
  • Spring permite únicamente rutas estáticas y API declaradas; las rutas no previstas se deniegan.
  • Los errores visibles usan role="alert"; los botones deshabilitan durante el guardado y los inputs tienen etiquetas asociadas.
  • Los cambios recientes tienen pruebas React para apertura/cierre y creación exitosa/fallida.

Limitaciones y verificaciones pendientes

  • No se inició la aplicación ni se inspeccionaron respuestas HTTP reales, cabeceras Set-Cookie, TLS, CORS, proxy inverso ni redirecciones.
  • No se ejecutaron ataques ni pruebas dinámicas de fuerza bruta, CSRF, sesiones concurrentes o aislamiento entre cuentas.
  • No se ejecutaron nuevamente las pruebas; el informe se basa en el código y resultados previos disponibles, no en una ejecución nueva.
  • No se midieron volúmenes reales de MongoDB, planes de consulta ni requisitos de datos por usuario.
  • No se inspeccionaron contenedores externos, backups, permisos de producción ni configuración de infraestructura fuera del workspace.
  • Las observaciones sobre cookies, credenciales y exposición operacional son condicionales hasta comprobar el entorno desplegado.

Criterio de confianza y cierre

Confianza alta significa evidencia directa en archivos fuente o configuración revisada. Confianza media significa que falta comprobación dinámica o medición de impacto. No se declararon vulnerabilidades críticas o altas por ausencia de evidencia suficiente. Este documento conserva recomendaciones anteriores relevantes y refleja el estado actual sin modificar código de aplicación.
